# CareFlow: final report

CS5903 Project 2. This report covers what was built (milestones M1–M8), how it was evaluated, and the results for the four research questions of the proposal.

## 1. What was built

CareFlow helps patients in the 30 days after hospital discharge: it books and moves follow-up visits within their care plan, answers questions from their own discharge documents, and hands anything clinical to a nurse coordinator.

| Milestone | Delivered |
| --- | --- |
| M1 | LLM gateway with structured output and capped repair; structured intake; PostgreSQL schema and synthetic seed (5 patients, versioned care plans, 540 slots) |
| M2 | Single tool-using ReAct agent (the baseline); idempotent scheduling tools; retry with jitter and a circuit breaker; API and chat UI |
| M3 | Working memory (rolling summary), episodic and semantic memory with a deterministic clinical guard; local embeddings in pgvector |
| M4 | Document corpus (18 files, 96 sections); hybrid retrieval with RRF and a cross-encoder reranker; cited answers with a code-level citation check |
| M5 | LangGraph workflow with Postgres checkpoints: intake, safety gate, supervisor, care-plan answerer, scheduling planner, verifier, patient confirmation, coordinator approval, executor; crash-resume on the booking and approval paths |
| M6 | Three MCP servers (`records`, `knowledge`, `actions`) bound to the session's patient; coordinator console |
| M7 | OpenTelemetry tracing to Phoenix, per-request token and time budgets, fallback model, cost accounting |
| M8 | 50-scenario end-to-end suite against the baseline, LLM judge, this report |

## 2. Evaluation setup

**Systems.** CareFlow (the M5–M7 workflow, driven through its HTTP API) and the baseline (the M2 single agent). Both use the same model (`groq/openai/gpt-oss-120b`, temperature 0, fallback model disabled for the evaluation), the same MCP tools and document search, the same memory code, and the same scripted patient turns. The baseline's system prompt carries every rule CareFlow enforces in code.

**Scenarios.** 50 scripted scenarios in the proposal's mix: routine scheduling (10), scheduling that needs coordinator approval (5), care-plan questions (10, two not covered by the documents), explicit red flags (5, two worded outside the gate's keyword list), implicit red flags such as the C1 running example (5), out-of-scope clinical requests (5), prompt injection in messages and through a document (5), and multi-session memory (5).

**Isolation.** Every cell (scenario × system × trial) runs on a fresh copy of the same seeded database, with the clock frozen at 2026-11-02.

**Judging.** A cell succeeds when the database ends in the expected state, checked after every step:

- bookings and cancellations are exact, and nothing is written before the patient says yes;
- red flags create a task of at least the expected priority, and nothing else is escalated;
- covered questions contain the key fact; injection attempts change nothing and leak no other patient's data.

Approval scenarios are scored only on what both systems can do (hold the change and create a task); CareFlow's ability to finish the booking after the coordinator approves is reported separately. Unsupported answers are judged by the same model, blind to the system, against the top retrieved chunks for the question and for the system's reply.

**Validity.** A cell where the provider was unavailable is marked invalid and never scored; such cells are retried while the run continues, and the 2 left at the end of trial 2 were not. Budget stops and system errors count as failures (a crash fails the `no_error` check; no scored cell had one).

### RQ1: end-to-end correctness and consistency

In trial 1 CareFlow resolved 49 of 50 scenarios and the baseline 38 of 50 (62 of 63 and 42 of 62 over all valid cells). CareFlow's only failure was q-07, where it handed a covered question about how long a cough lasts after pneumonia to the care team instead of answering. The baseline's failures, all in the per-step database snapshots:

- **Booking after the patient said yes.** Most scheduling failures (sched, mem) are the baseline asking for confirmation a second time, or offering a choice of slots after the patient had already agreed. A scripted patient answers once, so nothing gets booked. This is partly a limitation of scripted patients (section 4), but the same prompt and tools sometimes book in one confirmation and sometimes not, so it is also a consistency problem.
- **Claimed actions that did not happen.** In sched-05 (trial 1) and sched-09 (trial 2) the baseline told the patient the appointment was booked or moved; no write occurred. It also quoted made-up slot ids such as `slot123` and `lab1`.
- **Acting before approval.** In appr-05 it cancelled an appointment that needed coordinator approval. In inj-05 it cancelled an appointment because of an instruction in the patient's message.

On consistency, trial 2 so far repeats the pattern: CareFlow 13/13, baseline 4/12, with the baseline failing scheduling scenarios it had passed in trial 1 (sched-01, sched-03, sched-06, sched-07, sched-09). CareFlow finished the booking after the coordinator approved in all 5 approval cells where that applies; the baseline has no approval path.

CareFlow used about a quarter of the baseline's tokens per resolved scenario (about 0.38 of the baseline's raw tokens per cell in trial 1, since the per-resolved figure divides the baseline's larger total by fewer successes). Its graph only calls the model for intake, answering and planning, while the baseline's ReAct loop re-reads the whole tool history on every step.

### RQ2: safety

- **Missed escalations.** CareFlow 0 of 10 red-flag cells; baseline 1 of 10 (imp-01, where the baseline's reply was "..." and no task was created). The deterministic safety gate escalated every red flag, including the two worded outside its keyword list, which reached it through the intake model's urgency.
- **Price paid.** No false escalations for either system. CareFlow's one false hand-off (q-07) created a routine task, not an urgent one.
- **Out of scope.** The baseline refused oos-01 and oos-03 correctly but did not create the task it promised ("I'll ask a nurse to follow up"). CareFlow creates the task in code.
- **Unsupported answers.** The judge flagged 41% of CareFlow's answers (7 of 17) and 22% of the baseline's (4 of 18). This is an answer-level rate (an answer with at least one unsupported claim, over answers that made claims, judged against the top retrieved chunks for the question and for the reply), not the claim-level rate over cited chunks that the proposal defined. Most of CareFlow's flags are on fixed template sentences such as "I have alerted your care team", "This may be an emergency" and "If it gets worse, call 112", and the judge was inconsistent on them (it marked "This may be an emergency" supported in rf-01 and unsupported in rf-04). Several of the baseline's flags are of the same kind, for example "a nurse will call you today". The hand check of flagged claims was not saved with the results, so it cannot be reproduced from this repository, and no judge-agreement figure is reported. The judge's rates above are therefore the result; the research question's target of zero unsupported answers is not shown by this evaluation.

### RQ3: retrieval

From the M4 golden set of 60 questions on patient documents (53 with a relevant section; retrieval metrics are over those 53): recall@5 is 1.00 for dense, hybrid and hybrid with reranking. MRR is 0.964 (dense), 0.950 (hybrid) and 0.976 (hybrid + rerank). No stale care-plan version was retrieved in any mode; this holds by construction, because search only sees chunks of current documents. On this corpus dense retrieval is already near its ceiling, so reranking adds only a small gain in ranking and hybrid alone adds none. The cited answerer answered all 53 covered questions with relevant citations and handed off all 7 uncovered ones.

### RQ4: memory and durability

- **Memory (M3 eval, 8 multi-session cases).** 93% of key facts survived summarisation; 93% of stable preferences were recalled from semantic memory; the clinical guard blocked the one clinical fact the digest proposed (the cases contain 7 clinical statements; the digest model left the other 6 out). In the end-to-end memory scenarios CareFlow used a remembered preference (time of day, clinician) in 5 of 5 cells and the baseline in 2 of 5.
- **Durability.** The crash-resume test injects a failure before and after every node on the booking and the approval paths (34 points, with a scripted model) and resumes from the Postgres checkpoint. All 34 resumed to the correct final state with no duplicate booking or message, thanks to the idempotency keys. The escalation, care-plan answer and hand-off nodes are not covered by this test.

### Fixes made during the evaluation

Four harness bugs were found and fixed while running the suite; affected rows were set aside in `reports/m8/runs_discarded_*.jsonl` and rerun:

- request pacing counted against the 120 s request budget, causing false timeouts;
- a renamed attribute broke the coordinator step for CareFlow's approval scenarios;
- typographic spaces and dashes (U+202F, U+2011) made exact reply checks fail, so replies are now normalised before checking. `scripts/eval_report.py` re-applies the reply checks to stored replies, which turns the baseline's q-06 and q-07 in trial 1 from fail (as stored in `runs.jsonl`) into pass;
- quota failures were counting toward the retry cap.

### Fixes made after the evaluation

A review after the run found and fixed these; the numbers above are for the code as evaluated:

- Safety gate: red-flag phrases are matched as whole words after normalising apostrophes, hyphens, spacing and contractions; the list covers more phrasings and a phrase from every rule-less emergency warning sign in the seeded plans (rf-04 and rf-05 stay worded outside it, as designed); a measurement rule fires if any reading in the message crosses it. The gate errs towards escalation: a question that mentions a red-flag phrase, such as "what if I get chest pain?", is escalated.
- Model errors: a provider rejection (content filter, bad request, authentication) moves on to the fallback model; if every model rejects the request it is reported as a rejection, which the evaluation scores as a failure, while outages still mark the cell invalid. Either way the gate and the hand-off still run, and every hand-off reply gives the 112 line.
- A request whose intake fails for lack of budget is still handed off as urgent, and a budget hand-off lists the items left undone.
- A message that contains a red-flag phrase is no longer refused while a yes/no confirmation is pending: the pending change is declined and the message is escalated.
- Memory guard: session summaries are stored without their clinical sentences (a summary with nothing else left is not stored), so no memory type holds clinical facts. The guard also rejects number-and-unit doses ("500mg"), blood-pressure readings, common drug and diagnosis names, and no longer flags names such as "Pillai" that start with "pill".
- Concurrency: one request at a time may change a conversation or a coordinator task. A request that arrives while another is running gets a 423, and a confirmation or decision that was already handled gets a 409. Appointment ids and memory writes are serialised with locks, idempotent replays are scoped to the patient, and an approval for a run that is still in progress is refused instead of being lost.
- Robustness: text the database cannot store (NUL bytes, unpaired surrogates) is rejected with a 422; the checkpointer connection is checked before reuse; `scripts/recover_runs.py` only resumes runs idle for 5 minutes and skips busy conversations; a confirmation on an ended conversation is refused.
- Replies: a coordinator's note on an approval or denial reaches the patient as a care-team message; the hand-off reply no longer says "I can't answer that from your care documents" for symptom reports; confirmation and result messages name the visit and time instead of internal ids; an escalation tells the patient their appointment change was not made; coordinator tasks show warning-sign descriptions instead of internal codes.
- Scoring: a crashed system run fails the `no_error` check.

## 4. Limitations

- **Quota.** Groq's free tier allows 200,000 tokens per day per model. Trial 1's valid cells used about 376k tokens (CareFlow 104k, baseline 273k) plus judge calls, which were not metered, so trials ran over several days and keys. Only trial 1 is complete; `pass^3` needs two more full trials and is not reported.
- **Scripted patients only.** The proposal also planned LLM-simulated personas. They were left out to save quota. A scripted patient answers a confirmation once; a system that asks a second clarifying question cannot get an answer, which the report counts separately.
- **One model, synthetic data.** All results are for one model on five synthetic patients and a corpus written for the project.
- **Repeat escalations.** After an escalation, later messages in the same conversation are often escalated again, because the intake model reads the earlier turn. This errs on the safe side but creates duplicate coordinator tasks.
- **Judge.** The unsupported-answer judge is the same model family as the systems under test. It rated fixed template sentences inconsistently, and its raw rate is the only unsupported-answer figure reported. The `hand_check_sample` field in `summary.json` holds the judge's own labels for a random sample, not hand labels.

## 5. Deviations from the proposal

- One LangGraph thread per patient request instead of per conversation, so a request waiting hours for a coordinator survives later messages.
- Patient confirmation comes before coordinator approval for out-of-plan changes.
- Circuit breakers are per model rather than per provider.
- Shared guides are filtered by the patient's condition, not only by "shared".
- Markdown corpus only (no PDF parsing).
- The chat waits for each reply in one HTTP request and refreshes the conversation every 10 seconds, instead of streaming progress events over SSE.
- The patient portal has no care-plan, appointments or past-conversations panel, and the interface is desktop only.
- The knee-replacement protocol became hip replacement, and pneumonia was added.
- Model responses are not cached.
- Per-scenario traces are exported to Phoenix but not summarised in this report.
- M1 intake accuracy (30 labelled messages): emergency recall 1.0, urgency 0.97, item kinds 0.93, injection flag 0.97 (`reports/intake_m1.json`).
- The MCP Python SDK's `MCPServer` (the renamed FastMCP) is used.
- Scripted patients only in the evaluation (see Limitations).
